# Проект: SwipeSwap backend, выпуск v1.0

## 1. Паспорт проекта

**Участники:** Батсайхан Ширээт, Балабанов Максим.
**Продукт:** SwipeSwap — backend мобильной платформы бартерного обмена вещами без денег (ASP.NET Core 9, PostgreSQL, Redis, JWT).
**Планируемый выпуск:** `v1.0`
**Исходное состояние:** тег `baseline` = коммит `96e1706`.
**Репозиторий:** https://github.com/shireet/SwipeSwap

### Контекст и пользователи

Продукт разработан студентами в учебном проекте. Пользователи — мобильный клиент (в репозиторий не входит) и люди, обменивающиеся вещами: они регистрируются, публикуют вещи, предлагают обмен и договариваются в чате. Для них важны конфиденциальность аккаунта и переписки и то, что обменом и вещами управляет только владелец. Решение о выпуске принимают оба участника; при расхождении выпуск откладывается.

### Границы

**В проект входит:**

- backend;
- PostgreSQL и Redis в том виде, как их поднимает `compose.yaml`;
- `Dockerfile`, `compose.yaml`, GitHub Actions (`.github/workflows/ci.yml`);
- тесты: 89 unit-тестов;
- зависимости (`Directory.Packages.props`) и конфигурация (`appsettings.json`).

**За пределами проекта:**

- мобильный клиент;
- производственная инфраструктура, TLS, reverse proxy, облако;
- реальные пользователи и данные;
- рекомендации товаров: `Items/recommended` возвращает мок-данные.

### Компоненты, взаимодействия и границы доверия

- Клиент → REST API (`/api/v1/...`): основная граница доверия, всё из запроса недоверенное; аутентификация по JWT (HS256, срок 60 минут), refresh-токен действует 14 дней.
- API → PostgreSQL: пользователи (пароли в виде BCrypt-хеша), вещи, обмены, чаты, сообщения, refresh-токены. Миграции применяются при старте приложения.
- Источник кода → сборка: NuGet-зависимости, базовые образы Docker, GitHub Actions.
- Секреты (ключ JWT, пароль БД) читаются из `appsettings.json` и переменных окружения.

### Активы и существенные риски

- **Актив:** учётные записи и токены (`AuthenticateController`, `JwtService`, таблица refresh-токенов).
  **Что может произойти:** подделка токена при компрометации ключа JWT; попадание паролей и токенов в логи или в чужие руки.
  **Почему это существенно:** захват аккаунта и действия от чужого имени.
- **Актив:** обмены и вещи пользователей (`ExchangesController`, `ItemsController`).
  **Что может произойти:** действия над чужим обменом или вещью при слабой проверке прав доступа к объектам.
  **Почему это существенно:** это основная функция продукта, на ней держится доверие между пользователями.
- **Актив:** переписка в чатах и данные профиля (`ChatController`, `UserController`).
  **Что может произойти:** чтение чужих сообщений или персональных данных другими пользователями.
  **Почему это существенно:** нарушение конфиденциальности.
- **Актив:** секреты и конфигурация развёртывания (ключ подписи JWT, пароль БД; `appsettings.json`, `compose.yaml`, образ Docker).
  **Что может произойти:** утечка секретов через конфигурацию, образ или журнал.
  **Почему это существенно:** с ними можно выпускать валидные токены и обращаться к БД.
- **Актив:** цепочка поставки (NuGet-пакеты, образы, CI).
  **Что может произойти:** в выпуск попадают зависимости с известными уязвимостями.
  **Почему это существенно:** выпуск нельзя обосновать без проверки зависимостей.

## 2. Методологическая основа

**Основная рамка:** NIST SP 800-218, Secure Software Development Framework (SSDF), версия 1.1.
**Дополнительные источники:** OWASP ASVS 5.0.0, уровень 1 — только главы про аутентификацию, управление сессиями, токены, авторизацию, конфигурацию, защиту данных, журналирование и зависимости.

**Почему выбрана эта основа:** SSDF описывает практики разработки и выпуска, а не зрелость организации, поэтому подходит для небольшого продукта, двух участников и одного выпуска. Из SSDF берём процесс (что делать и когда), из ASVS — проверяемые требования к REST API с JWT, то есть то, что надо проверять в самом продукте.
**Что ещё рассматривали:** OWASP SAMM и BSIMM оценивают зрелость организации, для пары студентов избыточны; Microsoft SDL слишком тяжёл для срока курса; OWASP Top 10 — перечень рисков, а не процесс, используем его только для проверки полноты.

Выбранные положения SSDF (группа PO — подготовка, PS — защита ПО, PW — разработка, RV — реагирование на уязвимости):

### PO.1. Определить требования к безопасности

- **Что требует:** описать требования к безопасности и поддерживать их актуальными.
- **Почему применимо:** требований нет, а риски паспорта (захват аккаунта, доступ к чужим обменам и чатам) напрямую выражаются как требования.
- **Во что превращается:** короткий список проверяемых требований, выбранных из глав ASVS и привязанных к активам паспорта.
- **Признак выполнения:** каждое требование имеет проверку (тест, сканирование, осмотр) либо отметку «не проверяется» с причиной.

### PW.4. Зависимости

- **Что требует:** выбирать и поддерживать сторонние компоненты, проверять их на известные уязвимости.
- **Почему применимо:** выпуск включает транзитивные пакеты NuGet и базовые образы Docker.
- **Во что превращается:** воспроизводимая проверка состава зависимостей перед выпуском; High и Critical исправляются или оформляются как принятый риск.
- **Признак выполнения:** отчёт приложен к выпуску, для каждой записи есть решение.

### PW.7 и PW.8. Анализ кода и тестирование

- **Что требует:** анализировать код и тестировать работающий продукт на соответствие требованиям.
- **Почему применимо:** тесты проверяют только обработчики по отдельности, проверок прав доступа через HTTP нет.
- **Во что превращается:** изменения безопасности идут через pull request с ревью второго участника; требования авторизации проверяются тестами HTTP-запросов.
- **Признак выполнения:** тесты воспроизводимо проходят на выпуске и показывают недостаток там, где он есть на исходном состоянии.

### PO.3, PO.5 и PW.9. Инструменты, среда и безопасные настройки

- **Что требует:** автоматизировать проверки в сборке, защитить среду разработки и секреты, задавать безопасные настройки по умолчанию.
- **Почему применимо:** CI выполняет только `restore`, `build`, `test`; конфигурация и режимы запуска (Swagger, журналирование, порты) не разделены по окружениям.
- **Во что превращается:** проверки безопасности в CI, список проверки конфигурации выпуска, секреты задаются через окружение.
- **Признак выполнения:** CI-задачи проходят на выпуске; по каждому пункту списка конфигурации есть результат.

### RV.1 и RV.2. Выявление и устранение уязвимостей

- **Что требует:** искать уязвимости регулярно, оценивать и устранять по приоритету.
- **Почему применимо:** решение о выпуске должно опираться на результаты проверок.
- **Во что превращается:** список недостатков с приоритетом и статусом, закрытие высоких до выпуска или явное исключение, повторная проверка улучшения.
- **Признак выполнения:** по улучшению есть результат «до» и «после».

### PS.3. Архив и воспроизводимость выпуска

- **Что требует:** хранить выпуск так, чтобы его можно было воспроизвести.
- **Почему применимо:** оцениваются зафиксированные версии комплектов.
- **Во что превращается:** теги `baseline` (есть), `ek1`, `ek2` и версия выпуска (планируются); к выпуску прикладываются отчёты проверок.
- **Признак выполнения:** по тегу воспроизводятся сборка, тесты и проверки.

Рамка не переносится целиком: практики об обучении персонала, управлении поставщиками, раскрытии уязвимостей и подписи артефактов для пары студентов за семестр неприменимы и в проект не входят.

## 3. Текущее состояние

Исходное состояние — `baseline` (`96e1706`). Тег поставили сами участники после подготовки воспроизводимого запуска: на `84fdafc` добавлены описание запуска, `docker compose`, исправления конфигурации и сборки и CI на GitHub Actions. Продукт разрабатывается в одном репозитории; функциональность вливалась через pull request #1 и merge-коммиты. CI выполняет `restore`, `build` и `test`, тесты — 89 unit-тестов обработчиков бизнес-логики. На практике выпуск сводится к тому, что сборка проходит, а тесты зелёные; отдельных проверок безопасности и правил принятия решения о выпуске нет. Из хорошего: пароли хранятся как BCrypt-хеш, у JWT проверяются издатель, аудитория, срок и подпись, на контроллерах стоит `[Authorize]`, доменная модель `Exchange` проверяет статус и участника.

Выводы основаны на `README.md`, `.github/workflows/ci.yml`, `compose.yaml`, `Dockerfile`, `Directory.Packages.props`, тестах, коде контроллеров и middleware на `96e1706`, истории коммитов и pull request, а также на двух проверках: запуске API с просмотром журнала (`evidence/logging-leak.txt`, команды воспроизведения указаны в файле) и анализе зависимостей командой `dotnet list SwipeSwap.sln package --vulnerable --include-transitive`.

### Существенные разрывы

- **Разрыв:** критичные для безопасности свойства не проверялись воспроизводимо.
  **Почему важен:** корректность прав доступа к обменам и чатам определялась чтением кода, результат нельзя стабильно повторить перед выпуском. По коду есть признаки проблемы: идентификатор исполнителя обмена приходит из тела запроса, проверка участия в чате не выполнена.
  **Свидетельство:** все тесты в `tests/SwipeSwap.UnitTests` проверяют обработчики по отдельности, `tests/SwipeSwap.IntegrationTests/ApiTests/UnitTest1.cs` содержит пустой тест; `ExchangesController.cs` (`body.ActorUserId`), `ChatController.cs:35` (`// TODO: проверка, что пользователь — участник`). Признаки выявлены по коду, проверка запросами запланирована.
  **Приоритет:** высокий

- **Разрыв:** не было воспроизводимой проверки состава зависимостей.
  **Почему важен:** нельзя показать, что именно проверялось перед выпуском; ручной запуск находит пакеты с известными уязвимостями уровня High, достижимость которых в нашем коде неизвестна.
  **Свидетельство:** CI не анализирует зависимости (`.github/workflows/ci.yml`); команда `dotnet list SwipeSwap.sln package --vulnerable --include-transitive` на `96e1706` показывает `Npgsql 8.0.0` (GHSA-x9vc-6hfv-hg8c), `Microsoft.Extensions.Caching.Memory 8.0.0` (GHSA-qj66-m88j-hmgj) и `System.Text.Json 8.0.0` (GHSA-hh2w-p6rv-4g7w), все High. Эти пакеты приходят транзитивно через провайдер `Npgsql.EntityFrameworkCore.PostgreSQL 8.0.0` и EF Core 8.0.0 (`Directory.Packages.props`), поэтому исправление — обновление провайдера или явная фиксация версий.
  **Приоритет:** средний

- **Разрыв:** решение о выпуске не имело явной контрольной точки.
  **Почему важен:** успешная сборка и зелёные unit-тесты могут восприниматься как достаточное основание для выпуска, хотя они не проверяют безопасность. Нет письменных требований к безопасности и правил ревью изменений, поэтому непонятно, что именно блокирует выпуск.
  **Свидетельство:** `.github/workflows/ci.yml` — только `restore`, `build`, `test`; в репозитории нет документа с требованиями к безопасности, `CODEOWNERS`, шаблона pull request и правил ревью, теги выпусков не использовались. Настройки защиты веток в GitHub из репозитория не видны.
  **Приоритет:** высокий

- **Разрыв:** нет управления секретами и конфигурацией по окружениям.
  **Почему важен:** нет хранилища секретов и разделения настроек разработки и выпуска; выпуск запускается с настройками по умолчанию: Swagger включён без условия окружения, миграции применяются при старте, порты PostgreSQL и Redis опубликованы наружу, контейнер работает от root.
  **Свидетельство:** `src/SwipeSwap.WebAPI/appsettings.json` (единственный источник настроек), `Startup.cs:47-48,58`, `compose.yaml` (раздел `ports`), `Dockerfile` (нет `USER`).
  **Приоритет:** средний

- **Разрыв:** не определены правила журналирования и обработки ошибок.
  **Почему важен:** нет требования, какие данные можно писать в журнал и показывать клиенту: журнал содержит тела запросов и ответов, а при необработанной ошибке клиент получает внутренний текст исключения.
  **Свидетельство:** `Middleware/LoggingMiddleware.cs:17,36`, `Middleware/ExceptionHandlingMiddleware.cs:49`; `evidence/logging-leak.txt` — строки журнала после регистрации тестового пользователя с паролем и токеном в теле запроса и ответа.
  **Приоритет:** высокий
