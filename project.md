# Проект: SwipeSwap backend, выпуск v1.0

## 1. Паспорт проекта

**Участники:** Батсайхан Ширээт, Балабанов Максим.
**Продукт:** SwipeSwap — backend мобильной платформы бартерного обмена вещами без денег (ASP.NET Core 9, PostgreSQL, Redis, JWT).
**Планируемый выпуск:** `v1.0`
**Исходное состояние:** тег `baseline` = коммит `96e1706`.
**Репозиторий:** https://github.com/shireet/SwipeSwap

### Контекст и пользователи

Продукт разработан студентами в учебном проекте. Пользователи — мобильный клиент (в репозиторий не входит) и люди, обменивающиеся вещами: они регистрируются, публикуют вещи, предлагают обмен и договариваются в чате. Для них важны конфиденциальность аккаунта и переписки и то, что обменом и вещами управляет только владелец. Решение о выпуске принимают оба участника; при расхождении выпуск откладывается.

### Границы

**В проект входит:**

- backend;
- PostgreSQL и Redis в том виде, как их поднимает `compose.yaml`;
- `Dockerfile`, `compose.yaml`, GitHub Actions (`.github/workflows/ci.yml`);
- тесты: 89 unit-тестов;
- зависимости (`Directory.Packages.props`) и конфигурация (`appsettings.json`).

**За пределами проекта:**

- мобильный клиент;
- производственная инфраструктура, TLS, reverse proxy, облако;
- реальные пользователи и данные;
- рекомендации товаров: `Items/recommended` возвращает мок-данные.

### Компоненты, взаимодействия и границы доверия

- Клиент → REST API (`/api/v1/...`): основная граница доверия, всё из запроса недоверенное; аутентификация по JWT (HS256, срок 60 минут), refresh-токен действует 14 дней.
- API → PostgreSQL: пользователи (пароли в виде BCrypt-хеша), вещи, обмены, чаты, сообщения, refresh-токены. Миграции применяются при старте приложения.
- Источник кода → сборка: NuGet-зависимости, базовые образы Docker, GitHub Actions.
- Секреты (ключ JWT, пароль БД) читаются из `appsettings.json` и переменных окружения.

### Активы и существенные риски

- **Актив:** учётные записи и токены (`AuthenticateController`, `JwtService`, таблица refresh-токенов).
  **Что может произойти:** подделка токена при компрометации ключа JWT; попадание паролей и токенов в логи или в чужие руки.
  **Почему это существенно:** захват аккаунта и действия от чужого имени.
- **Актив:** обмены и вещи пользователей (`ExchangesController`, `ItemsController`).
  **Что может произойти:** действия над чужим обменом или вещью при слабой проверке прав доступа к объектам.
  **Почему это существенно:** это основная функция продукта, на ней держится доверие между пользователями.
- **Актив:** переписка в чатах и данные профиля (`ChatController`, `UserController`).
  **Что может произойти:** чтение чужих сообщений или персональных данных другими пользователями.
  **Почему это существенно:** нарушение конфиденциальности.
- **Актив:** секреты и конфигурация развёртывания (ключ подписи JWT, пароль БД; `appsettings.json`, `compose.yaml`, образ Docker).
  **Что может произойти:** утечка секретов через конфигурацию, образ или журнал.
  **Почему это существенно:** с ними можно выпускать валидные токены и обращаться к БД.
- **Актив:** цепочка поставки (NuGet-пакеты, образы, CI).
  **Что может произойти:** в выпуск попадают зависимости с известными уязвимостями.
  **Почему это существенно:** выпуск нельзя обосновать без проверки зависимостей.

## 2. Методологическая основа

**Основная рамка:** NIST SP 800-218, Secure Software Development Framework (SSDF), версия 1.1.
**Дополнительные источники:** OWASP ASVS 5.0.0, уровень 1 — только требования к авторизации, журналированию и обработке ошибок, зависимостям и конфигурации REST API.

**Почему выбрана эта основа:** SSDF описывает практики безопасной разработки и выпуска, встраивается в существующий цикл, а практики можно выбирать по рискам, поэтому подходит для небольшого REST API, двух участников и одного выпуска. ASVS не является рамкой процесса: это перечень проверяемых требований к приложению. Мы используем его только там, где SSDF слишком общий, как источник формулировок требований для PO.1 и критериев проверки.

Выбранные положения SSDF (группа PO — подготовка, PS — защита ПО, PW — разработка, RV — реагирование на уязвимости):

### PO.1. Определить требования к безопасности

- **Что требует:** описать требования к безопасности и поддерживать их актуальными.
- **Почему применимо:** требований нет, а риски паспорта (захват аккаунта, доступ к чужим обменам и чатам) напрямую выражаются как требования.
- **Во что превращается:** короткий список проверяемых требований; формулировки берём из ASVS (главы про авторизацию, журналирование и ошибки, зависимости, конфигурацию) и привязываем к активам паспорта.
- **Признак выполнения:** каждое требование имеет проверку (тест, сканирование, осмотр) либо отметку «не проверяется» с причиной.

### PW.4. Зависимости

- **Что требует:** выбирать и поддерживать сторонние компоненты, проверять их на известные уязвимости.
- **Почему применимо:** выпуск включает транзитивные пакеты NuGet и базовые образы Docker.
- **Во что превращается:** воспроизводимая проверка состава зависимостей перед выпуском; записи High и Critical исправляются или оформляются как принятый риск.
- **Признак выполнения:** отчёт приложен к выпуску, по каждой записи есть решение.

### PW.7 и PW.8. Анализ кода и тестирование

- **Что требует:** анализировать код и тестировать работающий продукт на соответствие требованиям.
- **Почему применимо:** тесты проверяют только обработчики по отдельности, проверок прав доступа через HTTP нет.
- **Во что превращается:** изменения безопасности идут через pull request с ревью второго участника; требования авторизации проверяются запросами к API.
- **Признак выполнения:** результат воспроизводится на теге выпуска и показывает недостаток там, где он есть на исходном состоянии.

### PO.3, PO.5 и PW.9. Инструменты, среда и безопасные настройки

- **Что требует:** автоматизировать проверки в сборке, защитить среду разработки и секреты, задавать безопасные настройки по умолчанию.
- **Почему применимо:** CI выполняет только `restore`, `build`, `test`; конфигурация и режимы запуска (Swagger, журналирование, порты) не разделены по окружениям.
- **Во что превращается:** проверки безопасности в CI, чеклист конфигурации выпуска, секреты задаются через окружение.
- **Признак выполнения:** CI-задачи проходят на выпуске; по каждому пункту чеклиста есть результат.

### RV.1 и RV.2. Выявление и устранение уязвимостей

- **Что требует:** искать уязвимости регулярно, оценивать и устранять по приоритету.
- **Почему применимо:** решение о выпуске должно опираться на результаты проверок.
- **Во что превращается:** список недостатков с приоритетом и статусом, закрытие высоких до выпуска или явное исключение, повторная проверка улучшения.
- **Признак выполнения:** по улучшению есть результат «до» и «после».

### PS.3. Архив и воспроизводимость выпуска

- **Что требует:** хранить выпуск так, чтобы его можно было воспроизвести.
- **Почему применимо:** оцениваются зафиксированные версии комплектов.
- **Во что превращается:** теги `baseline` (есть), `ek1`, `ek2` и версия выпуска (планируются); к выпуску прикладываются отчёты проверок.
- **Признак выполнения:** по тегу воспроизводятся сборка, тесты и проверки.

Рамка не переносится целиком: практики об обучении персонала, управлении поставщиками, раскрытии уязвимостей и подписи артефактов для пары студентов за семестр неприменимы и в проект не входят.

## 3. Текущее состояние

Объект — backend SwipeSwap, исходное состояние `baseline` (`96e1706`), планируемый выпуск `v1.0`. Дерево `master` (`288b1d6`) совпадает с этим тегом: merge pull request #2 не меняет файлы. Выборка — весь доступный репозиторий на `96e1706`: 33 коммита до тега включительно, оба влитых pull request (#1 и #2), workflow, тесты, конфигурация и код границ доверия. Производственных выпусков не было, поэтому контрольная точка «решение о выпуске» в истории не наблюдалась.

Тег `baseline` поставили участники после подготовки запуска. Описание запуска, `docker compose`, правки конфигурации и сборки и CI добавлены коммитом `9b8b0d8`, правка регистра путей для Linux — `96e1706`. CI на GitHub Actions выполняет `restore`, `build` и `test`. В репозитории есть unit-тесты обработчиков; интеграционный проект содержит один пустой тест. Отдельной процедуры безопасности и записи о решении выпустить версию нет.

**Сохраняем, пока нет причины заменять:** хеширование паролей BCrypt (`RegisterRequestHandler`, `LoginRequestHandler`); проверка издателя, аудитории, срока и подписи JWT (`DependencyInjection.ConfigJwt`); `[Authorize]` на контроллерах вещей, обменов, чата и пользователя; правила статуса и участника в `Exchange.Accept/Decline/Cancel/Complete`; запуск unit-тестов в CI.

Источники: `README.md`, `.github/workflows/ci.yml`, `compose.yaml`, `Dockerfile`, `Directory.Packages.props`, тесты, контроллеры и middleware на `96e1706`, история коммитов, GitHub API pull request #1 и #2, журнал `evidence/logging-leak.txt` и один запуск `dotnet list SwipeSwap.sln package --vulnerable --include-transitive`.

**Пока неизвестно:** включена ли в GitHub защита ветки `master` (из файлов репозитория это не видно); обсуждали ли дифф устно вне GitHub; достижим ли в этом коде каждый из найденных GHSA. Это открытые вопросы, а не доказанные дефекты.

### Существенные разрывы

- **Разрыв:** обещанное разграничение доступа к обменам и чатам не подтверждено воспроизводимым результатом.
  **Ожидание:** перед выпуском есть повторяемый результат, что действием обмена и чтением переписки управляет участник, а не произвольный идентификатор из запроса (паспорт; SSDF PW.8).
  **Почему важен:** это основное свойство доверия между пользователями. Чтение кода его не заменяет.
  **Свидетельство:** тесты в `tests/SwipeSwap.UnitTests` вызывают обработчики напрямую и передают идентификатор аргументом; `tests/SwipeSwap.IntegrationTests/ApiTests/UnitTest1.cs` пустой. В `ExchangesController` исполнитель берётся из `body.ActorUserId`, а не из JWT. В `ChatController.cs:35` остаётся комментарий, что проверку участия ещё нужно добавить; `GetChatMessagesHandler` и `SendMessageHandler` отбирают сообщения по `ChatId` без участника. `UserController.GetUser` отдаёт email любого пользователя любому аутентифицированному вызывающему.
  **Предел вывода:** это наблюдение кода и состава тестов на `96e1706`. Запрос, который подтвердил бы или опроверг обход, ещё не сохранён. Отсутствие такого запроса не объявляется уязвимостью.
  **Ближайший шаг:** получить результат HTTP-проверки на `baseline` (раздел 5, метод 1), а не менять код до этого результата.
  **Приоритет:** высокий — свойство выпуска нечем подтвердить, а проверка паре доступна локально.

- **Разрыв:** у выпуска нет сохранённой проверки состава зависимостей.
  **Ожидание:** перед `v1.0` есть отчёт о известных уязвимостях зависимостей и решение по каждой существенной записи (SSDF PW.4).
  **Почему важен:** выпуск включает транзитивные пакеты NuGet; зелёная сборка этот состав не показывает.
  **Свидетельство:** `.github/workflows/ci.yml` не анализирует зависимости. Один ручной запуск `dotnet list SwipeSwap.sln package --vulnerable --include-transitive` на `96e1706` показал `Npgsql 8.0.0` (GHSA-x9vc-6hfv-hg8c), `Microsoft.Extensions.Caching.Memory 8.0.0` (GHSA-qj66-m88j-hmgj) и `System.Text.Json 8.0.0` (GHSA-hh2w-p6rv-4g7w), уровень High, транзитивно через `Npgsql.EntityFrameworkCore.PostgreSQL 8.0.0` и EF Core 8.0.0 (`Directory.Packages.props`). Команда и версия SDK в отчёт не сохранены, файл отчёта в `evidence/` нет.
  **Предел вывода:** список относится к одному запуску и не доказывает, что уязвимый код вызывается приложением.
  **Ближайший шаг:** повторить команду, сохранить отчёт и отдельно решить достижимость. Обновление пакетов — только после этого.
  **Приоритет:** средний — пробел в обосновании выпуска есть, но сначала нужно отделить достижимые записи от шума.

- **Разрыв:** значимое изменение и выпуск не имеют второго взгляда и отдельной точки решения.
  **Ожидание:** изменение аутентификации, обменов, чата, владения вещами, журналирования, секретов или зависимостей смотрит второй участник; выпуск `v1.0` принимается по комплекту свидетельств конкретной версии, а не по зелёным unit-тестам (SSDF PW.7, PS.3).
  **Почему важен:** оба влитых pull request влиты автором без review, а прямые коммиты в `master` второго взгляда не оставляют. Неясно, что останавливает выпуск.
  **Свидетельство:** в GitHub у pull request #1 (автор и merge — Sheikhovskiy, 6 коммитов) и #2 (автор и merge — shireet, 2 коммита) ноль reviews и ноль комментариев. В репозитории нет `CODEOWNERS`, шаблона pull request и описания требований. CI — только `restore`, `build`, `test`. Продуктового тега выпуска нет, есть только учебный `baseline`.
  **Предел вывода:** выборка — все влитые pull request репозитория. Устное обсуждение вне GitHub не проверялось. Настройки защиты веток из клона не видны.
  **Ближайший шаг:** зафиксировать правило второго взгляда и состав комплекта `v1.0` (раздел 4). Защиту ветки проверить в настройках GitHub и записать результат.
  **Приоритет:** высокий — без этой точки остальные проверки не к чему приложить.

- **Разрыв:** секрет и режим запуска не отделены от настроек по умолчанию.
  **Ожидание:** ключ подписи и пароль базы не являются единственным зафиксированным в git способом запустить выпуск; режим, который показывает схему API и применяет миграции, явно привязан к окружению (SSDF PO.5, PW.9).
  **Почему важен:** с ключом JWT можно подписывать токены. Паспорт уже считает секрет активом. Учебные значения не отменяют отсутствие правила.
  **Свидетельство:** единственный набор настроек — `src/SwipeSwap.WebAPI/appsettings.json` (ключ JWT и пароль базы в репозитории). `compose.yaml` публикует порты PostgreSQL и Redis и задаёт пароль `password`. `Startup.cs` всегда включает Swagger (строки 47–48) и вызывает `Database.Migrate()` при старте (строка 58). В `Dockerfile` нет инструкции `USER`.
  **Предел вывода:** это настройки репозитория, а не осмотр чужого боевого окружения: его в границах проекта нет.
  **Ближайший шаг:** чеклист конфигурации на контрольной точке выпуска. Полное хранилище секретов и TLS вне границ проекта.
  **Приоритет:** средний — для учебного запуска секрет уже опубликован в репозитории, поэтому срочное «прятание» того же значения мало что меняет; правило для следующего изменения секрета и для выпуска нужно.

- **Разрыв:** журнал и ответ об ошибке не ограничены правилом о чувствительных данных.
  **Ожидание:** пароль, access- и refresh-токен не попадают в журнал, а клиент при необработанной ошибке не получает внутренний текст исключения (паспорт, актив «учётные записи и токены»).
  **Почему важен:** журнал регистрации уже содержит пароль и токен тестового пользователя. Это наблюдаемый след, не гипотеза.
  **Свидетельство:** `LoggingMiddleware` пишет тело запроса (строка 17) и тело ответа (строка 36). `ExceptionHandlingMiddleware.cs:49` отдаёт `ex.Message` с кодом 500. `evidence/logging-leak.txt` — журнал `POST /api/v1/authenticate/register` на `baseline`.
  **Предел вывода:** проверен один учебный запрос регистрации в локальном `docker compose`. Другие маршруты тем же прогоном не снимались.
  **Ближайший шаг:** повторяемая проверка журнала регистрации и входа входит в метод 2. Исправление логирования — кандидат на единственное улучшение курса, после сравнения с методом 1.
  **Приоритет:** высокий — след уже есть, свойство конфиденциальности учётных данных нарушается наблюдаемым поведением.

**В раздел 4 переходит:** сохранить unit-тесты, проверку JWT, BCrypt и доменные правила обмена; уточнить защиту ветки; ввести второй взгляд и комплект выпуска; не считать чтение кода доказательством прав доступа; не считать список GHSA доказательством достижимости.

## 4. Целевой Secure SDLC

Схема ниже — предложение для следующих изменений и для выпуска `v1.0`. Она не описывает уже проведённые проверки. Граница: backend, `compose.yaml`, образ API и GitHub Actions этого репозитория. Мобильный клиент, TLS, боевое облако и круглосуточное дежурство в схему не входят. Решение о выпуске принимают Ширээт и Максим вместе; если мнения расходятся, выпуск откладывается (раздел 1).

### Что меняем по диагнозу раздела 3

- Unit-тесты в CI, проверка JWT, BCrypt и правила `Exchange` — сохранить.
- Нет воспроизводимого результата по правам на обмены и чаты — перед выпуском и при изменении этих границ получать результат метода 1. До результата код не объявлять уязвимым и не переписывать «на всякий случай».
- Оба влитых pull request без review — для перечисленных ниже изменений обязателен второй взгляд до слияния.
- Нет точки выпуска — `v1.0` существует только как тег плюс короткий комплект свидетельств.
- Журнал уже пишет пароль и токен — на выпуске должен быть повторный след по регистрации и входу. Это главный кандидат на одно улучшение в рамках курса.
- Список GHSA без файла и без разбора достижимости — на выпуске сохранить отчёт и решение по записи, а не обещать обновить все пакеты.
- Секреты в git и всегда включённый Swagger — чеклист на выпуске. Отдельный сейф секретов и смена уже опубликованного учебного ключа не входят в обязательное ядро.

### Обязательное ядро

Для каждого изменения, которое затрагивает аутентификацию, обмены, чат, владение вещами, журнал, `appsettings.json`, `compose.yaml`, `Dockerfile`, `Directory.Packages.props` или `.github/workflows/ci.yml`:

1. Автор в описании pull request называет затронутое свойство из паспорта и что именно должен увидеть проверяющий.
2. Второй участник смотрит дифф до слияния и оставляет review в GitHub. Автор не вливает свой запрос.
3. CI по-прежнему выполняет `restore`, `build` и `test`. Красный результат останавливает слияние.
4. Если затронуто свойство из блока «по риску», к запросу приложен соответствующий след либо явная пометка, что след будет только на выпуске, потому что меняется не поведение, а комментарий.

Для каждого выпуска `v1.0` (и следующего, если он понадобится):

1. Версия — тег на коммите, который собирается.
2. Комплект: результат unit-тестов этой версии, результат методов раздела 5, открытые вопросы, чеклист конфигурации (ключ не добавлен новым значением в git, Swagger и `Migrate()` осознанно оставлены или ограничены, порты базы — как в `compose.yaml`).
3. Оба участника смотрят один и тот же тег. Зеленая сборка сама по себе выпуск не разрешает.

Остальные изменения (имена, тексты ошибок домена, правки README без секретов) идут обычным pull request с CI, без отдельного следа безопасности.

### Действия по риску

- Меняются `ExchangesController`, обработчики обмена, `ChatController`, обработчики чата или выдача профиля — нужен результат метода 1 на этой версии.
- Меняются `Directory.Packages.props`, базовый образ `Dockerfile` или наступает выпуск — нужен отчёт метода 2 о зависимостях.
- Меняются `LoggingMiddleware`, `ExceptionHandlingMiddleware` или наступает выпуск — нужен след журнала регистрации и входа без пароля и токена либо зафиксированное несоответствие, если исправление ещё не внесено.

### Путь изменения и две точки

1. Автор описывает свойство и открывает pull request.
2. **Слияние.** Проверяющий — второй участник. Он смотрит, затронуто ли свойство, есть ли требуемый след и прошёл ли CI. Сливает запрос проверяющий, не автор. Нет следа там, где он обязателен, — запрос не сливается, автор добирает след или сужает дифф.
3. Обычные unit-тесты остаются необходимым условием и не подтверждают права на чат, состав зависимостей и содержимое журнала.
4. **Выпуск.** Ответственный за комплект собирает результаты на теге. Второй сверяет, что файлы в `evidence/` относятся к этому тегу, а открытые вопросы названы. Выпуск разрешён только если оба согласны. Недостающий обязательный след останавливает выпуск: версию не помечают «готовой» с дырой в комплекте.
5. После выпуска сообщение о проблеме приходит issue в этом репозитории.

### Кто что делает

- **Второй взгляд на изменение границ доступа и журнала.** Ведёт Максим, если автор Ширээт, и наоборот. Проверяющий смотрит дифф и след метода, а не переписывает изменение. Решение о слиянии фиксирует review в pull request.
- **Комплект выпуска `v1.0`.** Ведёт Ширээт: тег, список свидетельств, открытые вопросы. Максим сверяет тот же тег и пишет в pull request или в `project.md`, что комплект открывается и относится к этой версии. Согласие обоих — единственное основание выпустить.
- **Метод 1** ведёт Максим, **метод 2** ведёт Ширээт. Подробности — в разделе 5. Автор метода не принимает собственный результат как независимую проверку.

Если второй участник недоступен дольше двух дней, автор не вливает изменение сам. Он оставляет запрос открытым. К дате выпуска недоступность второго участника означает отложить выпуск, а не назначить себя проверяющим.

### Если правила не выполнены

- **Нет результата.** Шаг стоит. Для слияния это решает проверяющий pull request, для выпуска — любой из двоих: достаточно одного «комплект неполный». Пока след не получен или вопрос явно не вынесен в остаточный риск выпуска, тег готовности не ставят. Вынести в остаточный риск можно только известное ограничение с владельцем и сроком, не пустой пункт.
- **Просьба пропустить правило.** Автор пишет, какое правило, почему не успевает, какой риск, на какой версии и до какой даты, чем компенсирует. Разрешает второй участник, не автор. Нет ответа второго — исключение не разрешено, шаг отложен. Преподаватель может сузить границы проекта; это не разрешение выпустить версию без обещанного свойства.
- **Сообщение после выпуска.** Канал — issue в `shireet/SwipeSwap`. Автор сообщения указывает тег версии. Второй участник подтверждает, что воспроизвёл влияние на этой версии. Исправление идёт тем же путём, что и обычное изменение, и закрывается повторным следом того метода, который свойство покрывает. Если причина в правиле, а не в разовой ошибке, правило в этом разделе меняют отдельным коммитом в `project.md`.

В курсе пара успевает ввести второй взгляд и комплект `v1.0`, снять свидетельства двух методов раздела 5 и сделать одно улучшение с повторной проверкой. Улучшение выбирается по результату «до»: либо перестать писать в журнал тела аутентификации и перестать отдавать внутренний текст необработанной ошибки, либо привязать исполнителя обмена и участника чата к субъекту JWT и закрепить это тестом. Оба улучшения сразу не обещаются. Обновление всех транзитивных пакетов, TLS, отдельный пользователь контейнера и хранилище секретов остаются за пределом этого выпуска, если метод 2 не покажет достижимую критичную запись.
